# Problem Discovery

## Inputs and Scope

- 사용자 요청에서 시작한다. 기존 비전·이슈·관련 코드·제약을 확인하고, 없는 문서를 사용자에게 먼저 작성하도록 요구하지 않는다.
- 이 단계는 제품 방향을 정하며 구조 설계·구현 계획은 다음 단계에 맡긴다. 범위와 대안은 [현재 필요에 맞는 해법](../harness-review/references/code-quality.md#proportional-solutions)으로 판단한다.
- 작성 전 [작성 규칙](../using-harness/references/authoring.md)과 [저장 경계](../using-harness/references/storage.md)를 적용한다. 여러 결정은 항목과 `(현재/전체)`를 알려 한 번에 하나씩 논의한다.

## Discovery

| Topic | Content |
| --- | --- |
| 문제·사용자 | 누가 어떤 상황에서 겪는 문제인지와 실제 근거 |
| 성공·핵심 흐름 | 달성할 결과와 확인 방법, 대표 사용자 흐름 |
| 범위 | 이번에 포함할 것과 제외할 것 |
| 대안 | 기존 방식·재사용·만들지 않는 선택을 포함한 실질적 대안과 선택 이유 |
| 제약·가정 | 알려진 제약, 미검증 가정과 확인 방법·재검토 조건, 구조를 좌우할 가정에 따라 재검토할 결정 |

- 관찰·사용자 경험·외부 근거·추정을 구분한다. 유효한 답을 다시 묻거나 대안·시장 조사·수치 목표를 의례적으로 만들지 않으며 대안 개수를 강제하지 않는다.
- 중요한 미결정은 사용자와 논의한다. 구조 설계에 남긴 질문을 탐색 누락으로 처리하지 않는다. 기술 탐색은 가능하나 미검증 가정을 확정 사실이나 승인된 결정으로 바꾸지 않으며, 구조·구현 세부는 필요한 다음 단계에 넘긴다.

## Records and Review

- `.harness/work/<work-id>/discovery.md`에 이번 문제·대안·선택 근거·남은 가정을 기록한다. 식별자는 [식별자 규칙](../using-harness/references/identifiers.md)을 따른다.
- [승인·검토 대상](../using-harness/references/approvals.md)을 보존하고 요구·제약·관련 비전·근거와 함께 `harness-review`에 독립 검토를 요청한다.
- 리뷰가 제기한 방향·범위·중요 가정 변경은 사용자와 논의한다. 의미를 보존하는 문서 수정에는 기존 승인 적용 규칙을 따른다.

## Next Stage

- 위 탐색 항목이 정리되고 필수 독립 리뷰를 통과한 검토 대상의 방향을 사용자가 승인하면 `harness-design`에 승인 대상·제약·남은 가정을 넘긴다. 탐색 승인을 구현 승인으로 해석하지 않는다.
- 새 제품의 승인된 방향은 `.harness/product/vision.md`에 반영한다. 기존 기능 탐색은 제품 방향이 바뀔 때만 비전을 수정한다. 선택 근거는 탐색 기록에 두고 비전에 복사하지 않는다.
- 근거가 부족하면 필요한 탐색을 이어가고, 사용자가 보류·중단을 정하면 그 상태를 남긴다. `CURRENT.md`에는 다음 행동과 관련 문서만 연결한다.
