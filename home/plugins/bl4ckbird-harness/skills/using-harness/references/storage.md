# Document Storage and Ownership

## Storage Boundary

생성한 에이전트 작업 기록은 프로젝트의 `.harness/`에 두고 `/.harness/`로 Git에서 제외한다. `docs/`는 실제 사용자 문서용이다. 플러그인의 실행 지침과 프로젝트에서 생성한 기록은 별개다.

| Location | Responsibility |
| --- | --- |
| `CONTEXT.md`, `CURRENT.md` | 프로젝트 안내, 진행 중 작업·중단 위치·다음 행동 |
| `product/vision.md` | 승인된 제품 목적·사용자·범위 |
| `architecture/index.md`, `architecture/<subject>.md` | 대상 프로젝트의 구조와 주제별 설계 |
| `decisions/<decision-id>.md` | 중요한 결정의 맥락·대안·결과 |
| `roadmap/index.md`, `roadmap/<milestone>.md` | 성과·순서·의존 관계·완료 기준 |
| `work/<work-id>/discovery.md`, `spec.md`, `plan.md` | 탐색, 상세 동작 명세, 구현 계획 |
| `work/<work-id>/state.json` | 해당 작업의 단일 현재 실행 상태 |
| 작업별 `reviews/`, `evidence/`, `snapshots/`, `approvals/`, `diagnosis/` | 리뷰·검증·보존 대상·승인·원인 조사 |

경로는 `.harness/` 기준이다. 내용이 생긴 문서만 생성하고 빈 전체 구조를 미리 만들지 않는다. 제품 코드·기호·주석·테스트·사용자 문서·생성물·브랜치·커밋·PR에 내부 ID·스킬명·작업 문서 경로를 남기지 않는다. 공개 이슈·제품 식별자와 구분한다. Git 제외 규칙과 하네스 자체의 정의·도구에는 필요한 경로·규약을 기술할 수 있으나 실제 프로젝트의 비공개 근거는 포함하지 않는다.

커밋·공개 전에 변경한 추적 파일·추가할 파일·생성 출력·커밋 메시지·PR 제목과 본문을 확인한다. 실제 내부 ID·기록 경로와 문맥상 참조를 제거하되 기능 검증을 약화하거나 기존 커밋 이력을 자동 재작성하지 않는다. 날짜 형태만으로 유출이라고 판정하지 않는다.

## Ownership and Size

- 같은 판단·규칙은 하나의 기준 문서에서 관리한다. 함께 읽고 바뀌는 내용은 묶고 독립적으로 참조·검토할 책임은 나눈다.
- 인덱스는 위치·상태를 안내한다. 본문·과거 논의·실행 로그를 복제하지 않는다.
- 줄 수나 파일 개수를 맞추려고 나누지 않는다. 중복과 낡은 내용을 먼저 정리하고, 무관한 장문을 읽어야 하는 부분을 분리한다.
- 현재 구조·상태는 갱신하되 과거 승인·리뷰·검증 대상은 보존한다. 계획은 진행 로그가 아니다. 완료 문서의 경로를 유지하고 활성 목록만 정리한다.
- 과거 논의는 별도로 보존하고 현재 판단의 기준이 아님을 표시한다. 문서를 나누면 현재 참조와 인덱스를 함께 갱신하고 보존된 승인·리뷰·검증 대상은 바꾸지 않는다.
- 작성·문서 리뷰·최종 동기화에서 이 기준을 적용한다. 형식 취향만으로 진행을 막지 않고 실제 누락·모순·오독 위험으로 판단한다.

새 내부 ID를 만들 때는 [식별자 발급 규칙](identifiers.md)을 읽는다. 문서 편집·검토만 할 때 발급 절차를 적용하지 않는다.
