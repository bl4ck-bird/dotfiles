# Writing Guidelines

## Language and Clarity

- Markdown 제목·헤딩과 표의 열 제목은 영어로, 본문·설명 메타데이터·리뷰 질문은 한국어로 작성한다. 기계 식별자·코드·명령·오류는 원문을 유지한다.
- 제품 코드·문서·커밋의 언어는 해당 프로젝트 규칙을 따른다. 하네스의 영어 헤딩 규칙을 제품 문서에 강제하지 않는다.
- 새 파일과 수정 부분부터 적용한다. 보존된 승인·리뷰 기록과 기존 영문 설계를 일괄 번역하지 않으며 이 규칙만으로 무관한 코드·기록을 재작성하지 않는다.
- 목적에 필요한 내용만 명료하게 쓴다. 중복·자명한 설명·불필요한 추상화를 줄이되 동작·필수 조건·판단 근거를 보존한다.
- 문서·스킬은 조건과 행동, 코드는 이름과 제어 흐름, 커밋·PR은 변경과 필요한 이유·검증·제약에 집중한다. 글자 수·짧은 변수명·한 줄 코드 자체를 목표로 삼지 않는다.
- [용어 기준](terminology.md)으로 단계·역할·판정을 구분한다. 모호한 합성어와 기계적인 명사 나열을 피한다.

## Responses

결론을 먼저 말하고 중요한 근거를 덧붙인다. 진행은 새 사실·불확실성·다음 행동, 리뷰는 문제·근거·미검증·판정, 완료는 변경·검증·남은 문제·전달 상태를 담는다. 빈 섹션·의례적 칭찬·작업 일지·반복 요약은 생략한다.

자세한 근거는 링크하되 답변만으로 결과와 중요한 제약을 알 수 있게 한다. 필요한 범위부터 읽고 유효한 근거를 재사용한다. 간결화 때문에 필수 필드나 요청한 검토 깊이를 생략하지 않는다.

## Decision Progress

여러 결정은 항목을 먼저 알리고 `(현재/전체)`로 질문한다. 같은 결정의 보충 질문은 번호를 유지하고 항목 변경 시 총수를 갱신한다. 잠정 총수·보류를 구분하며 질문 위치를 완료 개수로 취급하지 않는다. 중단 후 기존 작업 기록에서 이어 간다. 질문 수를 인위적으로 조절하거나 진행 표시용 문서를 따로 만들지 않는다.

## Structure

제목은 주제, 목록은 독립 항목, 번호는 순서, 표는 비교에 사용한다. 실행 지침의 상세 규칙은 필요한 시점에 읽도록 연결하되 불필요한 설명을 다른 파일로 옮겨 남기지 않는다. 설치 이력·설계 논의는 실행 지침에 넣지 않는다. 문서 분리는 [문서 관리 기준](storage.md#ownership-and-size)을 따른다.
