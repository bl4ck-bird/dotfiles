# Test Quality and Integrity

## Test Value

새 테스트를 선택·작성·리뷰할 때 다음을 확인한다.

| Criterion | Question |
| --- | --- |
| 보호할 동작 | 어떤 요구·불변식·회귀 위험을 검증하는가 |
| 결함 탐지 | 어떤 현실적인 오구현이면 실패하는가 |
| 독립 기대값 | 구현 계산이나 설정한 mock 반환값이 아닌 계약에서 기대 결과를 얻었는가 |
| 추가 가치 | 기존 검증에 없는 보호를 추가하며 유지 비용이 타당한가 |

짧은 테스트·존재 확인·호출 횟수·mock 사용 자체는 결함이 아니다. 실제 계약과 검증 범위를 본다. 핵심 동작을 대체해 놓고 전체 기능을 검증했다고 주장하지 않는다.

## Planning and TDD

동작·중요한 실패 조건부터 정하고 가장 좁은 유효 검증을 선택한다. 충분한 기존 검증과 필수 프로젝트·통합 검사를 유지한다. 동작 테스트가 유효하면 실패→구현→통과→정리를 적용하고 문서·기계적 작업에는 적절한 검증을 사용한다.

함수 부재의 실패는 시작일 수 있으나 함수 생성 후 통과만으로 충분하지 않다. 최종 단언이 중요한 오구현을 구분해야 한다. 테스트 개수·커버리지·TDD 순서만으로 품질을 주장하지 않는다.

## Changed Checks

기대값·snapshot·단언·fixture·mock·테스트 삭제/통합·skip·실행 설정이 바뀌면 승인된 동작이 여전히 검증되는지 확인한다. 구현의 현재 출력을 정답으로 삼거나 필수 검사를 숨기지 않는다. 기존 테스트가 틀렸거나 내부 세부에 결합됐다면 계약과 필요한 검증을 보존하며 수정할 수 있다.

재현 가능한 회귀는 수정 전 실패·후 통과를 확인한다. 실행할 수 없으면 한계를 남긴다. 중요한 의문에는 허용된 격리 환경의 결함 주입을 사용할 수 있으나 매 테스트마다 도구·점수·설명 문서·리뷰를 요구하지 않는다.

## Evidence

검사 실행 실패·테스트 미발견·건너뜀·실제 단언 실패를 구분한다. 불안정한 검사는 실패 이력과 재실행 이유를 보존하고 통과할 때까지 반복해 숨기지 않는다. 명세와 검증 기준 자체가 바뀌면 해당 사용자 검토가 필요하며 계약을 보존한 테스트 개선은 기존 실행 범위에서 처리한다.
