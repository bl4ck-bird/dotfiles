# 변경 명세

제품 방향·관련 도메인·공유 설계·현재 기준 명세와 실제 코드를 읽는다. 신규 프로젝트의 전체 설계가 없거나 중요한 공유 결정을 새로 해야 하면 `bl4ck-harness-design`으로 연결한다. 이미 합의한 대화를 다시 인터뷰하지 않고 실제 공백만 확인한다.

## 명세 내용

`changes/<변경명>/spec.md`에 문제·목표, 정상 흐름·실패/경계 상황, 입력·출력·데이터/권한 계약, 수용 기준, 제외 범위, 근거 문서와 미결정을 적는다. 기존 기준 명세의 전체 사본 대신 이번 차이를 설명한다. 수용 기준은 사용자가 관측할 수 있는 결과로 적고 중요 실패도 포함한다.

모듈 경계와 검증할 외부 동작을 명시한다. 실제 결정에 필요한 짧은 타입·상태 표·스키마는 허용하지만 함수 본문·완성 테스트·보일러플레이트·미래 파일 목록을 요구하지 않는다. 사용자 스토리를 길게 늘리는 것을 완전성으로 판단하지 않는다.

## 확인과 전달

요구 누락·모순·범위·모호한 용어와 미검증 가정을 먼저 정리한다. 중요한 명세는 `bl4ck-harness-review`로 독립 검토하고 사용자가 실제 내용을 확인한 뒤 `bl4ck-harness-writing-plans`로 연결한다. 작고 명확한 변경은 명세와 계획을 한 문서로 축약할 수 있으나 동작·검증·권한은 보존한다.

이 문서는 승인된 목표이며 현재 구현의 증거가 아니다. `specs/`는 검증 전 갱신하지 않는다. 승인 대상 사본과 실제 사용자 근거를 보존한다.
