# 도메인 모델링

기존 `design/domain.md`와 관련 결정을 읽는다. 단순히 용어집을 소비하는 작업과 모델 자체를 바꾸는 작업을 구분한다. 같은 개념에 다른 이름, 같은 이름에 다른 의미가 쓰이면 구체적인 사례로 확인한다. 유효한 맥락별 차이는 보존한다.

## 확인할 내용

- 핵심 개념의 정의와 서로 다른 개념 사이의 경계
- 관계·소유권·생명주기, 허용·금지되는 상태 전이
- 중복·취소·부분 실패·재시도 같은 실제 상황에서 유지해야 할 불변식
- 현재 코드·데이터와 설명의 일치 여부, 앞으로 바꾸려는 목표와 현재 동작의 차이

용어가 정리되면 바로 갱신한다. 용어집 영역에 구현 코드나 작업 로그를 넣지 않는다. 관계·상태·불변식은 별도 절로 구분하고, 서로 다른 도메인을 함께 읽어야 하는 부담이 커질 때만 주제별 파일과 짧은 안내로 나눈다. 처음부터 엔티티별 파일이나 DDD 계층을 강제하지 않는다.

중요한 결정 기록은 되돌리는 비용이 크고, 맥락 없이는 이유를 이해하기 어려우며, 실제 대안 사이의 선택이 있었을 때만 만든다. `decisions/`에는 맥락·대안·선택·영향과 적용 상태를 남긴다. 사소한 이름 선택마다 기록을 늘리지 않는다.

변경된 모델을 참조하는 제품·설계·명세를 식별한다. 구현이 아직 따르지 않으면 차이를 명시하고 기준 명세를 미래 상태로 바꾸지 않는다.
