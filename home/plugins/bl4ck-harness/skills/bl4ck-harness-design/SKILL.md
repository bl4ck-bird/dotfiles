# 전체 제품·시스템 설계

제품 방향·기능 지도·제약과 기존 근거를 읽는다. `bl4ck-harness-domain-modeling`과 `bl4ck-harness-codebase-design`을 적용해 설계를 구체화한다. 방향 자체가 불분명하면 `bl4ck-harness-brainstorming`으로 연결한다.

## 설계 범위

| 영역 | 결정할 내용 |
| --- | --- |
| 기능과 경험 | 기능군 관계, 핵심 흐름·상태·실패 경험, 초기 제공 범위 |
| 도메인 | 개념·관계·데이터 소유권·상태 전이·불변식 |
| 시스템 | 구성 책임·경계·의존 방향·데이터 흐름·외부 연동·공유 계약 |
| 기술 | 실행·배포 환경, 주요 스택, 버전·호환 제약, 선택 이유와 확인 근거 |
| 저장소 | 주요 디렉터리 책임, 모듈·공유 코드·테스트 위치와 의존 규칙 |
| 품질 | 핵심 수용 흐름, 보안·성능·복구 등 실제 위험과 검증 방향 |

변동 가능한 기술 선택은 공식 근거와 필요 시 작은 실험으로 확인한다. 사용자가 정한 스택을 임의 교체하지 않는다. 실제 대안이 있는 중요한 선택은 장단점과 추천 이유를 설명하고 합의한다. 화면이 중요한 제품은 화면·탐색·상태 흐름을 함께 확인하며 시각 자료가 필요하면 사용 가능한 도구로 만든다. 특정 디자인·프로토타입 플러그인을 필수 의존성으로 만들지 않는다.

## 작성과 깊이

도메인·구조·기술·저장소 책임을 공통 문서 기준에 따라 분리한다. 폴더 트리만 나열하지 말고 무엇을 어디에 두며 왜 의존하는지 설명한다. 함수 본문·모든 파일명·미래 기능별 상세 타입은 계획하지 않는다. 프로젝트 전체를 관통하는 결정과 가까운 구현에서 결정할 세부를 구분한다.

미결정 사항에는 영향·해결 시점·담당 단계를 적는다. 공통 구조나 첫 성과의 성립을 바꾸는 가정은 조사·사용자 결정으로 해결한다. 이후에 결정해도 현재 계약을 깨지 않는 사항은 명시적으로 미룬다.

## 다음 단계 조건

서로 다른 구현자가 이 자료를 읽고 공유 데이터·인증·상태 변경·인터페이스·폴더 책임을 서로 다르게 결정할 여지가 남았는지 확인한다. 중요한 결정을 새로 발명해야 한다면 설계가 준비되지 않은 것이다. 스택 이름과 기능 제목만 있는 문서는 통과하지 않는다.

`bl4ck-harness-review`로 제품 방향·설계·가정의 독립 검토를 받는다. 유효한 지적을 반영하고 실제 설계 내용에 대한 사용자 합의를 확인한 뒤 `bl4ck-harness-roadmap`으로 연결한다. 이미 로드맵이 있고 국소 설계 수정이면 영향받는 로드맵·명세만 재검토한다. 제품 scaffold도 구현이므로 이 조건을 우회하는 수단으로 사용하지 않는다.
