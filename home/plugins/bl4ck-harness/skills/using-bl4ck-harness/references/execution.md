# 배정과 수정 반복

## 배정

위임 도구와 권한이 있는지 확인한다. 모델 선택을 지원하면 현재 환경에서 제공하는 이름과 추론 수준으로 작업 위험에 맞게 선택하고 기록한다. 코드가 없는 계획을 단순 전사 작업으로 취급하지 않는다. 사용할 수 없는 모델을 만들어내거나 성능 우위를 단정하지 않는다.

요구와 근거는 파일로 인계한다. 배정에는 목표, 읽을 명세·해당 작업·공유 계약의 위치, 실제 편집 범위, 검증, 권한, 보고 위치만 담는다. 전체 대화·누적 이력을 복사하지 않는다. 구현자와 리뷰어는 하위 에이전트를 만들지 않는다. 배정·리뷰·공유 상태는 메인이 담당한다.

작고 동일한 형태의 독립 수정은 한 배정으로 묶고 모든 대상이 처리됐는지 검토한다. 구현을 병행하려면 파일뿐 아니라 공유 계약·데이터·테스트 자원·통합 순서가 독립인지 확인한다. 기본 구현은 순차 수행하고 독립 조사·검토는 병행할 수 있다.

대기 중에는 가능한 로컬 작업을 한다. 이벤트 기반 도구를 우선하고 짧은 반복 조회를 하지 않는다. 호스트가 허용하는 유한 대기를 사용하며 사용자에게 새 진행 사실을 알린다. 중단 요청과 실제 종료를 구분한다.

## 검토와 수정

위임 실행에서는 의미 있는 작업 단위마다, 인라인 실행에서는 계획의 연속 구현 후 전체 변경에 대해 독립 리뷰어 한 명이 명세 충족과 코드 품질을 각각 판정한다. 중요한 공유 계약·고위험 변경은 계획에 정한 중간 리뷰를 적용한다. 새 위험이 드러나면 영향받는 경계만 재검토하고 모든 작업에 리뷰를 일괄 추가하지 않는다. 구현자 자기 검토는 이를 대체하지 않는다. 기록된 실제 시작점부터 변경 전체를 확인하고 마지막 커밋 하나만 보지 않는다. 커밋이 없는 작업은 추적·스테이지·미추적 파일까지 포함한 기준 사본과 현재 파일을 비교한다.

같은 문제의 수정은 원 구현자를 재개하는 것이 기본이다. 재개할 수 없으면 작업·보고·시도 근거를 새 구현자에게 준다. 새로운 접근이 필요한 경우 담당자나 추론 수준을 바꿀 수 있으나 횟수는 유지한다. 매 수정 뒤 영향받는 검증을 수행하고 해당 지적과 수정 영향만 재검토한다.

한 작업의 수정·재검토는 최대 5회다. 진전 없는 반복이나 원인 불명은 한도 전에도 `bl4ck-harness-systematic-debugging`으로 보낸다. 5회 후 필수 문제가 남으면 영향받는 배정을 멈추고 원인·근거·다음 선택을 보고한다. 한도 소진을 완료나 자동 예외로 바꾸지 않는다. 경미한 관찰은 후속으로 기록할 수 있지만 수용 기준·보안·데이터 무결성 문제를 임의로 낮추지 않는다.

호출 자체의 실패는 원인을 확인한 뒤 같은 배정에서 최대 2회 복구한다. 실제 실행 여부가 불명확하면 충돌할 재호출을 먼저 하지 않는다. 구현 실패를 호출 오류로 분류해 수정 횟수를 초기화하지 않는다.
