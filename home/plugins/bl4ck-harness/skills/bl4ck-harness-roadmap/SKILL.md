# 로드맵

제품 목표·기능 지도·공통 설계를 읽는다. 목표를 확인할 수 있는 성과로 나누고 사용자 가치와 의존 관계로 순서를 정한다. 데이터베이스→서버→화면 같은 기술 계층만으로 단계화하지 않는다. 구조적 기반이 필요하면 어떤 성과를 가능하게 하는지 설명한다.

`ROADMAP.md`에는 성과·범위·완료 기준·선행 조건·관련 변경 링크·요약 상태를 둔다. 상세 작업 체크리스트·기능 본문·실행 로그를 넣지 않는다. 가까운 성과는 구체화하고 먼 성과의 세부는 유보한다. 순서가 바뀌어도 변경 폴더의 정체성은 유지한다.

재구성할 때 기존 완료 근거·미완료 변경·유효한 결정을 먼저 확인한다. 영향받는 범위와 의존 관계만 바꾸고 완료를 되돌리거나 기록 경로를 일괄 개명하지 않는다. 독립 제품·릴리스 관리가 실제 필요해지기 전에는 하위 로드맵을 만들지 않는다.

중요한 최초 로드맵이나 의존 관계 변경은 `bl4ck-harness-review`로 검토하고 사용자와 우선순위를 확인한다. 다음 성과의 한 변경을 `bl4ck-harness-spec`으로 연결한다. 실행 상태는 변경별 status를 기준으로 요약하며 로드맵 수정만으로 작업 완료를 만들지 않는다.
