# System Design Criteria

## Depth

다른 작업이 의존하거나 실패 시 구조·데이터를 크게 바꿔야 하는 결정은 시스템 설계에서 해결한다. 스키마·식별 키·트랜잭션·API/이벤트 의미도 정확성과 구조 성립에 필요하면 여기서 정한다. 공유 보장에 영향이 없는 내부 세부는 상세 명세로 미룬다.

## Ready for Roadmap

- 주요 선택이 요구·제약·위험과 연결된다.
- 핵심 불변식마다 책임 구성 요소와 보장 방법이 있다.
- 대표 흐름에서 정상·실패·복구가 연결된다.
- 구조 선택을 좌우하는 가정을 필요한 깊이로 조사·실험했다.
- 남은 질문에는 해결 시점과 기존 결정의 재검토 조건이 있다.
- 필수 독립 리뷰와 사용자 검토를 거쳤다.

## Evidence and State

실험은 가정·판단 기준·환경·방법·실제 관찰·설계 영향·한계를 기록한다. 실험 성공을 제품 구현 완료로 해석하지 않는다. 아직 만들지 않은 제품의 실행 검증을 설계 완료 조건으로 요구하지 않는다.

현재 구조·제안·승인·구현 상태를 구분한다. 미승인 제안으로 기준 문서를 덮어쓰지 않는다. 중요한 결정의 대안·근거·대체 관계를 보존하고 실제 구현 위치와 상태는 완료 단계에서 갱신한다.

## Domain Terms

용어가 책임·상태·인터페이스에 영향을 주면 사용자 언어와 실제 코드에서 뜻을 확인한다. 해당 설계·명세에서 정의하고 공통 개념을 독립적으로 유지할 필요가 있을 때만 별도 주제로 나눈다. UI·코드·외부 이름의 차이가 정당하면 연결 관계를 명시한다. 호환성에 영향을 주는 이름·의미 변경은 사용자와 설계한다.

정의에는 적용 범위와 혼동하기 쉬운 개념의 차이를 남긴다. 같은 단어라도 맥락별로 다른 의미가 유효하면 보존한다. 리뷰에서는 설계·명세·코드·테스트 간 의미와 UI·외부명 대응을 대조하며, 단순한 철자 차이를 결함으로 만들거나 모든 이름을 하나로 통일하지 않는다.
