# Root Cause Diagnosis

## Inputs and Scope

- 기대 동작·수용 근거, 증상, 코드·환경, 재현 절차, 로그·테스트와 이전 실패를 확인한다.
- 실행에서 넘어왔다면 같은 문제의 식별자·시도·남은 한도를 유지한다. 정보가 없으면 먼저 조사하고, 중요한 기대 동작이나 접근 불가능한 사실만 사용자 판단으로 돌린다.
- 작성·진단 기록에는 [작성 규칙](../using-harness/references/authoring.md)과 [저장·노출 경계](../using-harness/references/storage.md)를 적용한다.

## Investigation

- 실험마다 가설·지지/반박할 관찰·방법·실제 결과·결론을 남긴다. 정상/실패 경로 비교, 데이터 흐름 추적, 최소 재현 중 불확실성을 줄일 방법을 선택한다.
- 관찰·가설·미확인을 구분한다. 재현 실패를 해결 근거로 삼지 않는다. 실제 실행 증거로 원인을 설명할 수 있다면 로컬 재현의 한계를 명시한다.
- 승인 범위에서 재현 테스트·임시 계측을 만들 수 있다. 테스트에는 [테스트 품질](../harness-review/references/test-quality.md)을 적용하고 변경 파일·남은 계측을 보고한다. 사용자 변경을 함께 되돌리지 않는다.
- 실제 수정안을 적용·검증했다면 “진단 실험”이라는 이름으로 수정 시도에서 제외하지 않는다. [재시도 한도](../harness-execute/references/retries.md)와 [호출 복구 규칙](../harness-execute/references/resources.md)을 적용한다.
- 새 관찰 없이 반복하거나 필요한 접근·정보·합의한 자원이 부족하거나 한도에 이르면 근거와 막힌 이유를 반환한다. 모델 변경만으로 새로운 가설이라고 판단하지 않는다.

## Records and Report

`.harness/work/<work-id>/diagnosis/<issue-id>.md`에 증상·기대 결과·대상·재현·기각한 가설·원인·불확실성·수정안·회귀 검증·진단 변경·다음 행동을 정리한다. 관련 없는 문제를 한 파일에 누적하지 않는다.

| Status | Meaning |
| --- | --- |
| `Cause identified` | 원인을 뒷받침하는 근거 있음. 수정·검증 완료는 별도 |
| `Inconclusive` | 조사로 원인을 확정하지 못함 |
| `Blocked` | 필요한 정보·접근·자원 부족으로 조사 진행 불가 |

- 메인 에이전트에 상태·핵심 근거·수정 범위·보고 위치를 반환한다. 공유 실행 상태는 메인 에이전트가 확인해 갱신한다.
- [기존 승인](../using-harness/references/approvals.md) 안의 수정은 `harness-execute`로 연결한다. 중요한 동작·계약·구조 변경은 해당 설계와 사용자 검토로 돌린다.
- 진단 완료를 제품 결함 해결이나 독립 리뷰 통과로 기록하지 않는다. 재개·인계로 문제의 정체성이나 시도 횟수를 초기화하지 않는다.
