# Harness Entry

프로젝트와 현재 근거를 확인해 필요한 작업 단계로 연결한다.

## Activation

- 배정받은 에이전트는 배정 작업에서 시작한다. 프로젝트 초기화를 반복하지 않는다.
- [진입 설정](references/entry.md)을 읽고 프로젝트 루트·작업 기록의 기준 경로·활성화 상태를 확인한다.
- 설정 부재·비활성이면 자동 진입하지 않는다. 개별 스킬의 명시적 요청은 해당 스킬 조건으로 처리한다.
- 프로젝트 초기화·지속 활성화를 명시적으로 요청할 때만 최소 초기화를 한다. 스킬 읽기·단일 작업 적용 요청이나 `.harness/`의 존재는 그 권한이 아니다.
- 잘못된 설정·지원하지 않는 형식은 위치와 원인을 알리고 영향받는 절차를 보류한다. 일반 구현으로 필수 게이트를 우회하지 않는다.

## Evidence

- 요청·관련 코드·`CONTEXT.md`·`CURRENT.md`에서 단계 선택에 필요한 부분을 읽는다. 작업 기록이 없다는 이유로 새 프로젝트라고 판단하지 않는다.
- 이전 작업을 이어갈 때 [승인 적용](references/approvals.md)과 [실행 복원](../harness-execute/references/runtime.md)을 읽고 승인·리뷰·검증을 실제 상태와 대조한다.
- 결과의 존재와 실행 종료를 구분한다. 종료가 불확실하면 충돌할 작업을 보류하고, 유효한 승인·근거·재시도 이력을 보존한다.

## Entry Stage

[진입·축약 기준](references/entry.md)에 따라 선택한다. 근거가 바뀌면 영향받는 단계만 재평가한다.

| Current Need | Skill |
| --- | --- |
| 문제·제품 방향 정리 | `harness-discover` |
| 시스템 경계·공유 계약 설계 | `harness-design` |
| 성과의 우선순위·의존 관계 정리 | `harness-roadmap` |
| 기존 구조 안에서 새 동작 구체화 | `harness-spec` |
| 승인된 상세 명세의 구현·검증 계획 | `harness-plan` |
| 승인된 계획 실행·중단 작업 재개 | `harness-execute` |
| 원인 불명의 결함 조사 | `harness-diagnose` |
| 현재 단계의 독립 검토 | `harness-review` |
| 구현 후 최종 수용·전달 확인 | `harness-finish` |

## Routing and Records

- 문서·보고 작성 전 [작성 규칙](references/authoring.md), 작업 기록 생성 전 [저장 경계](references/storage.md)를 읽는다.
- 선택한 단계와 이유를 짧게 알리고, 대상·필요한 근거·유효한 권한을 다음 스킬에 전달한다. 해당 스킬의 선행 조건을 확인하고 진행한다.
- 구현 전 중요한 설계·명세·계획은 독립 리뷰 후 사용자와 검토한다. 승인된 실행은 재확인 없이 이어 간다.
- 부족한 근거는 먼저 조사하고 중요한 미결정만 묻는다. 필요한 스킬이 없으면 영향받는 절차와 부족한 대상을 알린다.
- 활성 프로젝트의 작업이나 다음 행동이 바뀌면 `CURRENT.md`를 갱신한다. 비활성 프로젝트의 단일 호출에는 초기화·진행 기록을 자동 요구하지 않는다. 활성화나 단계 선택을 구현 승인·완료로 기록하지 않는다.
