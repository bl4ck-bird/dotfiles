# Code Quality

## Design and Maintainability

| Criterion | Check |
| --- | --- |
| 책임·응집도 | 함께 바뀔 동작을 묶고 무관한 변경 이유는 분리 |
| 의존 방향 | 핵심 정책이 UI·프레임워크·저장소·외부 API의 세부에 종속되는 영향 |
| 추상화·중복 | 실제 복잡도 제거·같은 정책 중복·경계 보호에 필요한가 |
| 타입·입력 | 외부 값의 검증·변환 위치, 불가능한 상태의 차단 |
| 오류·부수 효과 | 성공·실패·남은 상태가 계약과 일치하고 오류를 숨기지 않는가 |
| 가독성 | 이름·제어 흐름이 실제 책임을 표현하는가. 축약·한 줄 코드가 목적이 되지 않는가 |
| 복잡한 도메인 | 불변식·상태 전이·소유·일관성 경계가 명확한가 |

SOLID는 실제 관계에 적용한다. SRP는 변경 이유, OCP는 실제 변형 요구, LSP는 교체 구현의 보장, ISP는 호출자가 알아야 하는 기능·권한, DIP는 외부 세부와 핵심 정책의 의존 방향을 확인한다. 구현 하나에도 경계 보호는 유효할 수 있으나 단순 CRUD에 계층·인터페이스를 의례적으로 추가하지 않는다.

## Proportional Solutions

- 현재 요구·수용 기준과 실제 사용 경로를 만족하는 가장 단순한 해법부터 검토한다. 미래에 생길 수 있다는 이유만으로 기능·설정·확장 계층·운영 체계를 추가하지 않는다. 필요한 확장은 구체적인 요구나 관측된 제약으로 정당화한다.
- 새로 만들기 전에 프로젝트의 기존 코드·라이브러리·도구·사용 가능한 스킬로 해결할 수 있는지 확인한다. 요구·권한·수명 관리가 맞으면 재사용하고, 맞지 않는 부분만 보완한다. 이름이 비슷하다는 이유로 의존성을 추가하거나 기존 절차 전체를 복제하지 않는다.
- 더 복잡한 해법이 필요하면 단순한 대안이 충족하지 못하는 현재 조건과 추가 유지 비용을 기존 설계·명세·계획에 짧게 설명한다. 이를 위해 별도 문서·게이트를 만들지 않는다.
- YAGNI는 리뷰어에게도 적용한다. 추가 기능·일반화·재작성을 요구하기 전에 실제 호출자·승인 계약·실패 근거를 확인한다. 추측성 미래 대비는 필수 수정이나 완료 차단 조건으로 삼지 않는다. 호출자가 보이지 않는다는 사실만으로 공개 API·외부 소비자·보존 데이터의 호환성을 삭제하지 않는다.
- 단순화할 때 관련 구현·호출자·설정·문서·테스트를 함께 대조한다. 삭제된 기능을 전제하는 검사는 정리하고, 유지하는 동작·실제 위험·기존 자료 호환성을 보호하는 검증은 남긴다. 간결함을 위해 필수 보장을 약화하지 않는다.

## Changed Boundaries

| Trigger | Check |
| --- | --- |
| 입력·반환·이벤트·공유 타입 | 수정하지 않은 호출자의 계약 파손·변경 전파 |
| 공유 상태·비동기·재진입 | 경쟁·교착·중복 효과·완료 순서 의존 |
| 연결·파일·작업·구독 | 실패·취소를 포함한 자원 수명·미해제 |
| 금액·시간·수량·식별자 | 단위·정밀도·시간대·범위·직렬화 |
| 데이터량·호출·운영 실패 | 무제한 처리·반복 쿼리·재시도 증폭·원인 확인 가능성 |

관련된 항목만 검토하며 모든 작업에 새 테스트·벤치마크·관측 도구를 요구하지 않는다. 중요한 제품 수치·취소·반올림 동작은 구현자가 임의로 정하지 않는다.

## Comments and API Documentation

코드로 드러나지 않는 이유·제약·불변식·외부 시스템 특이사항을 주석에 남긴다. 동작 반복·튜토리얼·변경 이력 주석은 피하고 관련 코드 변경 시 주석도 확인한다. 필요한 공개 API 문서는 입력·결과·오류·제약을 설명할 수 있다. 무관한 주석·이름 정리로 작업을 확대하지 않는다.
