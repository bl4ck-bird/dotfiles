# Worktrees and Shared Resources

격리는 실제 충돌·검증·사용자 변경 보호에 필요할 때 선택한다. 읽기 전용 리뷰와 이미 격리된 작업에 새 워크트리를 강제하지 않는다.

## Existing Workspace

- 요청한 기준과 `git status`, `git worktree list`를 확인한다. 연결 워크트리와 서브모듈을 구분하고 기존 격리 안에 워크트리를 중첩 생성하지 않는다.
- 코드 경로와 프로젝트 `.harness/` 기준 경로를 구분해 배정한다. 같은 프로젝트에 경쟁하는 기록 저장소를 만들지 않는다.
- 같은 계약·migration·공유 파일을 바꾸는 작업은 순차 실행한다. 코드를 병행 수정하려면 별도 워크트리를 사용하고 공유 데이터베이스·서비스·테스트 자원의 충돌도 확인한다.

## Provisioning

1. 승인 범위와 기준 코드를 지원하는 호스트의 워크트리 도구·프로젝트 도구·사용 가능한 스킬을 먼저 확인한다. 적합하면 생성·등록·정리를 그 절차에 맡기고 Git 명령으로 중복 관리하지 않는다. 도구 사용을 위해 무관한 새 태스크·의존성을 만들거나 설치·커밋 권한을 확대하지 않는다.
2. 적합한 도구·스킬이 없으면 실제 저장소에서 기준 커밋·브랜치·목적지를 확인하고 `git worktree add`를 사용한다. 사용자 배치 지침·기존 격리를 우선하며, 별도 지침이 없으면 Git에서 제외한 `.worktrees/<작업명>`을 사용한다. 제품 브랜치에 내부 ID를 넣지 않는다. 미커밋 변경은 자동 상속되지 않으므로 필요한 선행 변경만 승인 범위에서 옮기고 내용을 대조한다. 임의 stash·reset·최초 커밋은 하지 않는다.
3. 기존 계획/작업 기록에 경로·브랜치·기준·현재 세션의 생성 여부·정리 권한을 짧게 남긴다. 이름만으로 소유·삭제 권한을 판단하지 않는다.
4. 저장소 연결·기준 코드·필수 입력·접근·검증 환경을 확인한다. 패키지 설치·서비스 시작은 해당 권한 안에서 수행한다.

필수 격리가 실패하면 원래 공간을 조용히 수정하지 않는다. 부분 생성은 실제 경로·브랜치·Git 등록을 대조해 필요한 작업만 이어가며 자동 삭제로 복구하지 않는다.

## Handoff and Cleanup

서브에이전트에게 실제 코드·기록 경로와 권한을 전달한다. 승인 문서에 접근할 수 없으면 허용된 고정 사본을 작업 공간의 `.harness/`에 제공한다. 권한 우회용 심볼릭 링크는 만들지 않는다.

결과·리뷰 근거는 기준 기록에 회수하고 변경을 합친 실제 코드에서 통합 검증한다. 폐기할 공간에 고유 변경·유일한 근거를 남기지 않는다. [정상 정리 절차](../../harness-finish/references/delivery.md#cleanup)를 따른다.
