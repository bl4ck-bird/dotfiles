# 구현 계획

승인된 명세·관련 설계와 코드·필수 검증 명령을 확인한다. 계획은 구현 방법을 강제로 전사시키는 코드 문서가 아니라 목표를 실행 가능한 작업과 검증으로 연결하는 문서다.

## 작업 분해

`changes/<변경명>/plan.md`에 목표와 기준 명세, 실행 권한, 작업·의존 관계·통합 검증을 적는다. 각 작업에는 변경할 책임과 실제 위치, 필요한 입력·제공할 계약, 수용 결과, 검사 명령·환경·기대 결과를 둔다. 아직 없는 경로는 새로 만들 위치임을 구분한다.

가능하면 좁지만 처음부터 끝까지 검증할 수 있는 동작으로 나눈다. 테스트→구현→정리 행동마다 별도 작업 ID를 만들지 않는다. 설치·문서·설정은 해당 성과에 묶는다. 반복적인 같은 형태의 작은 수정은 한 배정으로 묶을 수 있다.

넓은 호환 변경은 새 계약 추가→호환 상태에서 호출자 이행→옛 계약 제거 순으로 나눈다. 중간 단계가 독립적으로 통과할 수 없다면 공동 통합 범위와 최종 검증을 명시한다. 파일이 다르다는 이유로 병행 가능하다고 판단하지 않는다.

## 세부 수준

각 작업의 입력·출력·제약·검증은 구체적으로 쓰되 완성 함수·테스트 코드를 반복하지 않는다. 코드가 있어야 정확한 공유 계약만 짧게 표현한다. 구현자는 승인된 경계 안에서 내부 방식을 선택할 수 있다. 단순 파일 수·예상 2~5분 같은 고정 크기로 분해하지 않는다.

요구가 암시하는 입력·경계 조건·실패 경로 중 기존 테스트와 계획된 검증이 빠뜨린 것이 있는지 확인한다. 실제 위험이 있는 누락만 해당 코드를 맡는 작업의 검증에 연결한다. 별도 문서나 고정 개수의 항목을 만들지 않고, 기존 검증으로 충분한 항목은 반복하지 않는다.

## 검토와 실행

수용 기준마다 구현·검증 위치를 연결하고 작업 간 공유 파일·인터페이스 충돌을 점검한다. 별도 인터페이스를 각 작업이 임의 정의하지 않게 한다. 실행 전 대상 경로·격리 필요·패키지 설치·커밋 등 권한과 최종 전달 지점을 명시한다.

`bl4ck-harness-review`로 요구 정합성·실행 가능성·통합 누락을 검토하고 사용자에게 실제 계획을 확인받는다. 아이디어·범위에 대한 동의를 아직 작성되지 않은 계획의 승인으로 간주하지 않는다. 이미 합의된 동일 범위의 실행 승인은 반복하지 않는다. 실행 방식은 작업의 독립성·위험·조정 비용에 따라 추천하고 기존 사용자 선택을 유지한다. 인라인은 연속 구현 후 전체 독립 리뷰를 기본으로 하며, 중요한 공유 계약·고위험 변경의 중간 리뷰가 필요하면 계획에 그 경계를 정한다. 위임 실행을 선택했고 도구와 권한이 있으면 `bl4ck-harness-subagent-driven-development`, 없거나 인라인 실행을 선택했으면 `bl4ck-harness-executing-plans`로 연결한다. 문서가 길다는 이유로 중요한 공유 계약을 실행 중에 추측하도록 남기지 않는다.
