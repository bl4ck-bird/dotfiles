# 설계와 문서의 독립 검토

메인은 작성자와 다른 리뷰어에게 현재 대상, 요구·제약·권한, 관련 자료, 확인할 위험과 보고 위치를 전달한다. 리뷰어는 대상 수정이나 추가 위임을 하지 않는다. 구현 결과는 `bl4ck-harness-requesting-code-review`의 기준으로 검토한다.

## 검토 관점

| 대상 | 핵심 질문 |
| --- | --- |
| 제품 | 사용자·문제·범위·성공 기준과 기능 관계가 분명한가? |
| 설계 | 공유 결정이 충분해 서로 다른 구현자가 호환되지 않게 만들 여지가 없는가? 도메인·스택·데이터 흐름·폴더 책임이 연결되는가? |
| 로드맵 | 성과·순서·의존 관계·완료 기준이 목표를 실현하는가? |
| 명세 | 정상·실패·경계 동작과 수용 기준이 명확하며 공통 설계에 부합하는가? |
| 계획 | 요구를 실행 가능한 작업·검증에 연결하고 통합·권한·실제 명령을 확인했는가? |

문서의 존재·길이·파일 개수를 통과 기준으로 삼지 않는다. 아직 필요하지 않은 미래 세부는 결함이 아니다. 중요한 가정을 구현자가 새로 결정해야 하는 공백, 현재와 목표의 혼동, 중복 기준과 낡은 참조를 찾는다. SOLID를 문서의 책임과 의존 관계에도 적용한다.

## 보고

`reviews/`의 새 보고에 대상 사본/해시, 범위, 지적 위치·발생 조건·근거·영향·해결 조건, 미검증과 판정을 남긴다. 심각도는 `치명`, `중요`, `경미`; 판정은 `통과`, `수정 필요`, `판정 불가`로 구분한다. 필수 근거가 없으면 지적이 없더라도 통과가 아니다.

메인은 실제 근거로 지적을 확인하고 유효한 문제를 담당 단계에 반영한다. 재검토는 이전 지적과 수정 영향에 집중하고 과거 대상·지적 ID를 보존한다. 보고서 자체가 사용자 승인이나 실행 권한을 부여하지 않는다.
