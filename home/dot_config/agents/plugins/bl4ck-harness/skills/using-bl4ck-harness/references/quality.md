# 품질과 검증

## 구현과 설계

현재 요구를 만족하는 가장 단순한 해법을 선택한다. SOLID는 책임·계약·의존 관계에 적용하고, 실제 복잡성 제거·중복 해소·경계 보호가 필요할 때 추상화를 추가한다. DDD는 도메인의 복잡성에 맞춰 사용한다. 미래의 가능성만으로 계층·전략·운영 절차를 늘리지 않는다.

기존 구조·호출자·데이터 흐름을 확인한다. 변경에 관련된 타입·오류·권한·자원 수명·정밀도·동시성·복구 계약을 검토한다. 성능 목표가 있으면 측정 조건과 결과로 확인한다. 공개 인터페이스는 입력·결과·오류·제약을 설명한다. 주석은 코드만으로 드러나지 않는 이유·불변식에 집중한다.

## 테스트와 증거

- 수용 기준을 관측 가능한 검증에 연결한다. 기존 필수 검사를 유지하고 충분한 기존 검증은 재사용한다.
- 테스트의 기대값은 요구와 독립적인 근거에서 도출한다. 구현 결과나 mock 반환을 그대로 기대값으로 반복하지 않는다.
- 실제 잘못된 구현을 하나 가정해 이 검증이 잡는지 확인한다. mock 호출 수만으로 제품 동작을 검증했다고 판단하지 않는다.
- 동작 변경은 실패하는 회귀/수용 검증 → 최소 구현 → 통과 → 필요한 정리로 진행한다. 설명·링크 수정에 동작 없는 테스트를 만들지 않는다.
- 실제 명령·위치·환경·대상 버전·결과를 기록한다. 검사를 실행했다는 보고와 결과 증거를 구분한다. 미실행·불명확·건너뜀은 통과가 아니다.
- 관련 수정 뒤 영향받은 검증을 다시 수행한다. 같은 코드에 충분한 근거가 있으면 이유 없이 전체 검사를 반복하지 않는다. 근거가 오래됐거나 다른 대상을 검사했으면 갱신한다.
- 완료 전 프로젝트가 정한 필수 검사 명령 전체의 결과를 확인한다. 개별 테스트 파일 통과만으로 전체 완료를 선언하지 않는다. 현재 대상에 이미 유효한 결과가 있으면 재사용하되 변경으로 영향받은 검사는 다시 수행한다. 기존 실패를 포함해 실행에서 발견한 모든 실패의 이름·영향·근거를 보고하고, 기존 문제라는 이유만으로 필수 검사를 통과 처리하지 않는다.
- 화면이나 연결 동작이 수용 기준이면 실제 사용자 흐름으로 확인한다. 구조 검사·스크린샷 하나·모의 서버만으로 전체 동작을 통과 처리하지 않는다.

검증 실패를 숨기기 위해 assertion·필수 검사·수용 기준을 약화하지 않는다. 기록 검사 도구는 형식·경로만 확인하며 내용의 정합성·사용자 승인·기능 품질을 증명하지 않는다.
