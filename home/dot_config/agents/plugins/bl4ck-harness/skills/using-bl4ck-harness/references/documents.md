# 문서의 책임과 저장

## 저장 경계

이 경로들은 프로젝트 루트의 `.harness/` 기준이다. 실제 사용자·개발자 문서인 `docs/`와 에이전트 기록을 구분한다. `.harness/`는 Git에서 제외한다. 이미 추적 중인 자료는 임의 추적 해제·삭제하지 않고 이관 범위를 확인한다.

| 위치 | 책임 | 갱신 담당 |
| --- | --- | --- |
| `CURRENT.md` | 현재 위치, 진행 중 변경, 미해결 결정, 다음 행동과 관련 링크 | 실행을 조정하는 메인 에이전트 |
| `ROADMAP.md` | 달성할 성과, 범위·의존 관계·완료 기준과 변경 링크 | `bl4ck-harness-roadmap` |
| `product/overview.md` | 사용자·문제·목표·제약·범위 | `bl4ck-harness-brainstorming` |
| `product/capabilities.md` | 전체 기능군과 관계, 초기 제공 범위 | `bl4ck-harness-brainstorming` |
| `product/experience.md` | 주요 사용자 흐름·상태·경험 기준 | `bl4ck-harness-design` |
| `design/domain.md` | 용어·관계·상태·불변식·소유권 | `bl4ck-harness-domain-modeling` |
| `design/architecture.md` | 구성 책임·경계·의존 방향·공유 계약 | `bl4ck-harness-design` |
| `design/technology.md` | 기술 선택·이유·제약과 검증된 근거 | `bl4ck-harness-design` |
| `design/repository.md` | 주요 폴더 책임·배치·허용 의존 관계 | `bl4ck-harness-design` |
| `specs/<기능>.md` | 구현·검증된 현재 기능 계약 | 완료 시 `bl4ck-harness-finishing-a-development-branch` |
| `changes/<변경명>/spec.md` | 이번 변경의 목표·동작·수용 기준 | `bl4ck-harness-spec` |
| `changes/<변경명>/plan.md` | 구현 단위·순서·연결·검증 계획 | `bl4ck-harness-writing-plans` |
| `changes/<변경명>/status.md` | 해당 변경의 현재 실행 상태와 근거 연결 | 실행을 조정하는 메인 에이전트 |
| `changes/<변경명>/reviews/`, `evidence/`, `snapshots/`, `approvals/` | 검토·검증·대상 사본·승인 근거 | 배정받은 기록 작성자, 상태 확정은 메인 |
| `decisions/`, `research/` | 별도 보존 가치가 있는 결정과 조사 근거 | 해당 결정을 조사·설계하는 스킬 |

내용이 있을 때만 생성한다. 작은 변경에 제품·설계 문서를 전부 만들지 않는다. 이름은 목표를 드러내며 순서 번호가 경로의 정체성이 되지 않게 한다. 하나의 로드맵으로 시작한다. 독립적으로 관리해야 할 제품·릴리스가 실제로 생기기 전에는 로드맵을 하위 폴더로 쪼개지 않는다.

## 책임과 참조

- 문서는 독자·책임·변경 이유에 따라 분리한다. 함께 읽고 바뀌는 내용은 묶고, 무관한 장문을 읽어야 이해할 수 있는 부분은 분리한다. 파일 수·줄 수 목표를 두지 않는다.
- 같은 계약과 결정의 기준은 한 곳이다. 인덱스·로드맵·현재 상태에 본문·체크리스트·과거 논의를 복사하지 않는다. 담당자는 기준을 수정하고 영향을 받는 참조만 맞춘다.
- 코드에 반영된 전체 폴더 트리·타입·함수를 문서로 복제하지 않는다. 저장소 문서는 책임과 비자명한 배치 이유를 유지한다. 필요한 실제 경로는 구현 계획에서 현재 코드로 확인한다.
- 상위 설계를 바꿔야 하는 내용을 개별 계획에만 적어 우회하지 않는다. 제품 범위는 제품 문서, 공통 구조는 설계 문서, 이번 변경만의 동작은 변경 명세에 둔다.

## 문서의 수명

`product/`와 `design/`은 합의한 방향을 담는다. 아직 구현되지 않은 결정은 목표 상태임을 표시한다. `specs/`는 검증된 현재 동작을 담으므로 문서 승인만으로 갱신하지 않는다. 변경 명세는 기준 명세를 참조하고 차이를 적는다. 완료 검증 후 그 차이만 현재 명세에 반영하고 변경 기록은 보존한다. 구현이 끝나기 전에는 새 동작을 현재 계약으로 표시하지 않는다.

현재 기준 문서는 갱신하되, 승인·리뷰가 대상으로 한 내용은 사본과 해시로 보존한다. [기록 도구](tools.md)의 `snapshot`을 사용할 수 있다. 사본 없이 과거 승인 대상을 덮어쓰지 않는다. 낡은 문서는 대체 문서를 표시하고 활성 참조를 갱신한다. 완료 변경 폴더를 자동 이동·삭제하지 않고 상태로 구분한다.

## 제품 결과물의 내부 정보

에이전트 내부 작업·슬라이스·리뷰 ID, 배정·재시도 내용, 스킬명, 비공개 기록 경로와 작업 지시를 제품 코드·주석·테스트·문서·생성물·브랜치·커밋·PR에 남기지 않는다. 필요한 이유는 제품의 동작·계약으로 다시 쓴다. 공개 이슈·실제 제품 식별자는 별개다. 하네스 자체의 정의·도구·출처 문서에는 제품인 하네스의 식별자와 규약이 필요할 수 있지만 실제 사용자 프로젝트의 비공개 기록은 넣지 않는다.

작성·리뷰·전달에서 실제 대상과 메시지를 확인한다. 단순 숫자·날짜·경로 패턴만으로 위반을 판정하지 않는다. 파일에서 내부 표식을 지우는 것으로 기능 검증을 약화하거나 기존 커밋 이력을 재작성하지 않는다.
