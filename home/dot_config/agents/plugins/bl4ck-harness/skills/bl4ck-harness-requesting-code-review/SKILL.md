# 구현의 독립 검토

메인은 기준 명세·해당 작업·공유 제약·실제 변경 범위·검증 보고와 리뷰 출력 위치를 전달한다. 리뷰어에게 작성자의 결론이나 특정 문제를 지적하지 말라는 지시를 주지 않는다.

시작점부터 실제 결과까지의 변경을 파일로 준비한다. 여러 커밋이면 전체 범위를 포함한다. 미커밋·미추적 파일도 확인하고 사용자 기존 변경과 작업 변경을 구분한다. Git이 없으면 기록한 사본·현재 파일과 명세로 범위를 확인한다.

리뷰어 한 명이 `명세 충족`과 `코드 품질`을 각각 `통과`, `수정 필요`, `판정 불가`로 보고한다. 실제 코드와 호출자를 읽고 요구·오류·보안·복구·테스트·문서·내부 정보 노출을 변경 위험에 맞춰 검토한다. 이미 같은 대상에 충분한 검증이 있으면 반복 실행하지 않되 근거 공백은 직접 확인하거나 미검증으로 남긴다.

명세에 예시가 없다는 이유만으로 합리적으로 기대되는 입력의 실패를 경미한 문제로 낮추지 않는다. 요구·공개 계약·기존 동작을 근거로 판단하며 새로운 제품 요구를 임의로 추가하지 않는다. 판단하지 못한 동작은 이유와 영향과 함께 기존 미검증 사항에 남기고 메인이 추가 확인·범위 조정·권한 있는 예외 중 필요한 처리를 결정한다.

지적에는 심각도·위치·조건·근거·영향·해결 기준을 붙인다. 변경 밖의 요구도 필요한 범위에서 확인하며 확인할 수 없으면 그 사실을 남긴다. 리뷰어는 코드 수정·추가 에이전트 호출·공유 상태 확정을 하지 않는다.

메인은 `bl4ck-harness-receiving-code-review`로 처리한다. 실행 방식에 맞춘 검토 뒤에는 계획된 통합 검증과 전체 변경의 연결·수용 기준을 확인한다. 동일한 전체 검토를 명칭만 바꾸어 반복하지 않는다.
