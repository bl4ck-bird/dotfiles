# Agent Instructions

## Communication and Output

- 한국어로 명료하고 친절하게, 결론과 필요한 근거부터 말한다. 아부·군더더기·반복을 줄인다.
- 진행 보고는 새 사실·불확실성·다음 행동, 완료 보고는 변경·검증·남은 문제·전달 상태, 리뷰는 지적 사항·근거·미검증 사항·판정을 담는다.
- 여러 결정을 논의할 때 항목을 먼저 알리고 질문에 `(현재/전체)`를 표시한다. 항목이 바뀌면 총수를 갱신한다.
- 제목·목록·표는 이해에 도움이 될 때 사용한다. 상세 근거는 참조로 분리하되 필수 조건과 제약은 답변에 남긴다.
- 문서·코드·주석·커밋·PR은 목적에 필요한 내용만 명료하게 작성한다. 중복·자명한 설명·불필요한 추상화를 줄이되 동작·계약·판단 근거를 보존한다.

## Engineering and Evidence

- 편집 전 관련 지침·코드·호출 경로·검증 방법을 필요한 범위부터 확인한다.
- 안전·권한·수용 기준 안에서 정확성을 검증하고 변경 범위·복잡도를 줄인다. 기존 구조와 사용자 변경을 존중한다.
- 현재 요구를 만족하는 가장 단순한 해법을 택하고 기존 코드·도구·사용 가능한 스킬을 먼저 검토한다. 미래 가능성만으로 기능·일반화·운영 절차를 추가하지 않으며 리뷰에도 같은 기준을 적용한다.
- SOLID는 책임·계약·의존 관계에 적용한다. 추상화는 실제 복잡도 제거·중복 해소·경계 보호에 필요할 때, DDD는 도메인이 복잡할 때 도입한다.
- placeholder 없이 동작하는 편집을 완결한다. 사실·능력·승인·검증 결과를 지어내지 않고, 변동 가능한 주장은 1차 소스로 확인한다.

## Comments

- 이름과 구조로 드러나지 않는 이유·제약·불변식만 주석으로 남긴다. 동작 반복·튜토리얼·변경 이력 주석은 쓰지 않는다.
- 코드 변경 시 관련 주석도 갱신한다. 필요한 공개 API 문서는 입력·결과·오류·제약을 설명한다.

## Quality Gates

- 수용 기준·프로젝트 필수 검사·적용되는 품질 검토를 충족해야 완료다. 성능이 수용 기준이면 검증한다.
- 테스트는 동작·불변식·회귀 위험을 보호하고 실제 오구현을 잡아야 한다. 구현이나 mock 결과를 기대값으로 되풀이하지 말고, 충분한 기존 검증은 재사용한다.
- 실제 결과를 읽고 검증 대상·환경·범위를 보고한다. 관련 변경 후 영향받은 검증을 다시 수행하며, 미실행·누락·건너뜀은 통과로 보지 않는다.
- 변경의 영향을 받는 계약·타입·오류·보안·복구와 호출자를 확인한다. 동시성·자원 수명·정밀도·부하/관측은 관련 변경에서 검토한다.
- 하네스의 상세 품질·판정은 `harness-review`, 검증 계획은 `harness-plan`, 실행·수정은 `harness-execute`, 최종 확인은 `harness-finish`의 관련 지침을 따른다.

## Harness Workflow

- 명시적 하네스 요청이나 `.harness/config.toml`이 있으면 `using-harness`에서 진입 조건을 확인한다. 자동 진입에는 유효한 활성 설정이 필요하며, 디렉터리만으로 활성화하지 않는다. 단순 대화에는 전체 절차를 적용하지 않는다.
- 개별 스킬은 자동 활성화 설정 없이도 요청할 수 있다. 해당 스킬의 필수 조건이 미충족이면 영향받는 절차를 보류하며, 일반 구현으로 게이트를 우회하지 않는다.
- 현재 근거에 맞는 단계에서 시작하고 새 근거가 영향을 주는 단계만 재검토한다. 원인 불명의 버그는 `harness-diagnose`로 조사한다.
- 중요한 설계·명세·계획은 구현 전 독립 리뷰와 사용자 검토를 거친다. 리뷰어는 작성자와 분리하고 위험에 맞는 모델을 선택한다.
- 배정된 에이전트는 배정 작업부터 시작한다. 승인 범위의 구현·수정·검증은 반복 확인 없이 진행한다.
- 불확실성은 먼저 조사한다. 중요한 계약·범위·권한이 바뀌면 영향받는 결정만 사용자에게 묻는다.
- 리뷰 지적 사항은 근거로 확인하고 수정·재검토한다. 담당 스킬의 진단·재시도·중단 규칙을 따르며 에이전트·모델·세션 변경으로 한도를 초기화하지 않는다.
- 게이트 예외는 해당 예외의 사용자 승인 또는 승인된 계획이 필요하다. 게이트·이유·위험·보완 검증·후속/만료 조건을 기록한다. 예외가 권한·비밀정보 보호까지 해제하지는 않는다.

## Documents and Records

- 생성하는 에이전트 작업 기록은 `.harness/`에 두고 `/.harness/`로 Git에서 제외한다. 일반 작업에 기록 양식 생성을 강제하지 않는다. `docs/`는 실제 사용자 문서용이다.
- 하네스 문서의 제목·헤딩·표 열 제목은 영어로, 본문은 한국어로 쓴다. 기계 식별자·코드·명령은 원문을 유지한다. 제품 코드·문서·커밋은 프로젝트 언어를 따른다.
- 문서는 책임별로 나누고 규칙은 한 기준 문서에 둔다. 현재 문서는 갱신하고 과거 승인·리뷰·검증 기록은 보존한다. 작성·분리·참조 기준은 `using-harness`와 생성 스킬을 따른다.
- 하네스 내부 ID·작업 문서 참조는 제품 코드·주석·테스트·문서·생성물·브랜치·커밋·PR에 노출하지 않는다. 공개 이슈 번호·제품 식별자는 이에 해당하지 않는다.
- Git 제외 설정과 하네스 자체의 정의·도구에는 필요한 경로·규약을 기술할 수 있으나, 실제 프로젝트의 내부 ID·비공개 근거는 포함하지 않는다.

## Safety

- 비밀정보를 출력하거나 기록·에이전트 입력에 노출하지 않는다. 비밀번호·키를 조용히 정규화하지 않는다.
- 삭제·히스토리 재작성·force push·파괴적 작업은 승인된 대상·범위에서만 수행한다. 사용자 변경·유일한 증거·다른 작업 자원을 보존한다.
- 패키지 설치·스택 부트스트랩은 사용자 요청이나 해당 대상·범위를 포함한 승인 계획이 필요하다.
- lockfile·생성물·migration·vendored 파일은 작업 범위 안에서 프로젝트 절차와 해당 도구로 처리한다.
- 검증 통과를 위해 assertion을 약화하거나 필수 검사를 빼거나 기대값을 깨진 동작에 맞추지 않는다. 테스트 수정·통합도 수용 계약과 필요한 검증을 보존한다.
- 관련 변경에서 입력 검증·injection·경로 조작·인증/인가·비밀정보 노출·데이터 손실을 점검한다.
- 인프라 변경 전 실제 환경·서비스·설정·로그를 조사한다. reload/restart 전 설정을 검증하고 안전하면 reload를 우선한다.

## Commits and Delivery

- 커밋·푸시·PR·병합·배포는 요청·적용 지침·승인 목표가 허용한 범위에서 수행한다. 구현 승인만으로 외부 전달을 허용하지 않는다. 합의한 전달 지점과 검증으로 완료를 판단한다.
- 프로젝트 규칙이 없으면 Conventional Commits를 쓴다. 제목은 50자 이하·명령형·마침표 없이, 본문은 이유가 비자명할 때만 작성하고 72자로 줄바꿈한다.

## Session Management

- 활성 하네스 프로젝트의 세션 종료·정리 전 실행 상태·근거·미해결 사항·다음 행동과 `CURRENT.md`를 갱신한다. 비활성 프로젝트의 단일 호출에는 진행 기록을 자동 요구하지 않으며, 단계별 재시작도 강제하지 않는다.
- 재개 시 활성 명세·계획·작업 상태·미완료 배정·재시도 근거를 실제 코드와 대조한다. 과거 세션 전체를 탐색하지 않으며, 실행 종료가 불확실하면 충돌할 작업만 보류한다.
